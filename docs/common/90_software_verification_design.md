# ソフトウェア検証設計

> **位置づけ**：本ドキュメントは ASPICE [SWE.6（Software Verification）](https://en.wikipedia.org/wiki/Automotive_SPICE) に該当する。
> ソフトウェア要件（`20_software_requirements.md`）の各要件に対し、統合されたソフトウェアがそれを満たすことを確認する検証ケースを定義する。
> 各 SWV は、対応するソフトウェア要件（SWR_NNN）へのトレースを持つ。

本書では、承認済みのソフトウェア要件に対する検証ケースを、要件の派生元システム要件ごとに整理して記述する。
検証の実施は段階4-4 で行う。

## 検証手段の分類

各検証ケースは `method`属性で検証手段を示す。分類は IADT に従う。

| 値 | 手段 | 内容 |
| --- | --- | --- |
| `inspection` | 検査 | 成果物を目視または静的解析で確認する。実行を伴わない |
| `analysis` | 解析 | 計算・モデル・シミュレーションにより間接的に確認する |
| `demonstration` | 実証 |実行し、期待する動作が観測できることを確認する。定量的な計測を伴わない |
| `test` | 試験 | 実行し、定量的な合否基準に対して計測値を判定する |

`environment` 属性は検証を実施する環境を示す。`host`（開発マシン上）、
`target`（RP2040 実機）、`ci`（GitHub Actions）、`review`（人手による確認）のいずれか。

## 検証ケースの構成

各検証ケースは以下の3項目を持つ。

- **前提条件**：検証を実施できる状態の定義。依存する実装段階と必要な計測手段
- **手順**：実施者が再現できる粒度の操作列
- **合否基準**：観測結果に対する判定条件。可能な限り数値で表現する

1つの検証ケースで複数の要件を確認できる場合は、`verifies` に複数の要件 ID を列挙する。

検証ケースの ID（SWV_NNN）は要件 ID（SWR_NNN）と対応しない。
1つの要件が複数の検証ケースを必要とすることも、1つの検証ケースが複数の要件を確認することもある。
対応関係は `verifies` 属性が正であり、番号の一致は偶然である。

前提条件には、対象要件を実装したソフトウェアが動作していることと、観測手段が利用できることを書く。
実装を担当する段階番号や内部コンポーネント名は書かない。
SWE.6 は統合されたソフトウェアが要件を満たすことを確認するプロセスであり、内部構造への言及はコンポーネント検証（SWE.5.2）の領域である。
またアーキテクチャは段階2.5-1 で作り直すため、現時点のコンポーネント名を埋め込むと再設計の結果に連動して修正が必要になる。

本書で初出の略語は、初出箇所で展開形を併記する。

## SYS_001（温度の継続的変化可視化）からの派生要件の検証

```{swverif} ADC初期化と温度センサチャネル選択の確認
:id: SWV_001
:status: draft
:method: demonstration
:environment: target
:verifies: SWR_001

**前提条件**

- SWR_001 を実装したソフトウェアが RP2040 実機で動作していること
- UART ログ出力が利用できること

**手順**

1. ADC 初期化後、ADC の制御レジスタと入力選択レジスタの値を UART に出力する
2. 温度センサのバイアス有効化ビットの状態を UART に出力する
3. ADC 変換を1回実行し、取得した生値を UART に出力する

**合否基準**

- 入力チャネルとして ADC チャネル4 が選択されていること
- 温度センサのバイアスが有効であること
- 取得した生値が 0 でも 0xFFF でもないこと（室温付近で飽和していないこと）
```

```{swverif} DMA転送の継続性とラップアラウンドの確認
:id: SWV_002
:status: draft
:method: test
:environment: target
:verifies: SWR_002

**前提条件**

- SWR_002 と SWR_007 を実装したソフトウェアが RP2040 実機で動作していること
- リングバッファの内容と DMA の書き込み位置を UART で観測できること

**手順**

1. リングバッファ全体と DMA の現在の書き込み位置を 1 秒間隔で UART に出力する
2. リングバッファが 3 周する時間以上（バッファ長 × サンプリング周期 × 3 以上）動作させる
3. 各出力における書き込み位置と、バッファ内の値の更新状況を記録する

**合否基準**

- 書き込み位置がバッファ長で折り返し、途切れずに進み続けること
- ラップアラウンド後もバッファの全要素が更新され続けること
- 転送されたデータが 16bit 単位で欠落なく並んでいること（ADC の変換結果として妥当な範囲に収まり、バイト境界のズレがないこと）
```

```{swverif} DMA転送のCPU非介入の確認
:id: SWV_005
:status: draft
:method: demonstration
:environment: target
:verifies: SWR_002

**前提条件**

- SWR_002 を実装したソフトウェアが RP2040 実機で動作していること
- gdb により CPU を停止させた状態で DMA の転送カウンタを読み出せること

**手順**

1. サンプリングを開始し、DMA が転送している状態を確認する
2. gdb でブレークポイントを設定し、CPU を停止させる
3. CPU 停止中に DMA の転送カウンタを 2 回、一定期間を空けて読み出す

**合否基準**

- CPU 停止中も DMA の転送カウンタが進んでいること
- CPU 停止中も ADC FIFO のオーバーフローフラグが立たないこと
```

SWR_002 は「DMA 転送を行うこと」と「CPU 介入なしに継続すること」の 2 つを要求している。
前者は動作を計測すれば確認できるが、後者は動作している事実からは証明できないため、
CPU を停止させた状態で転送が継続することを示す別の検証ケースを設ける。

```{swverif} サンプリング周期100Hzの計測
:id: SWV_003
:status: draft
:method: test
:environment: target
:verifies: SWR_003

**前提条件**

- SWR_003 を実装したソフトウェアが RP2040 実機で動作していること
- GPIO のトグル出力をロジックアナライザまたはオシロスコープで観測できること

**手順**

1. ADC サンプリング開始時に GPIO をトグルする計測用コードを有効化する
2. 10 秒間動作させ、トグル間隔を記録する

**合否基準**

- トグル間隔の平均が 10ms ± 0.1ms の範囲内であること
- 連続する 1000 回の計測で 10ms ± 0.5ms を外れる回数が 0 であること
```

```{swverif} I2Cバス初期化と通信確立の確認
:id: SWV_004
:status: draft
:method: demonstration
:environment: target
:verifies: SWR_004
:open_params: TBD-010 I2C速度が未確定のため、合否基準の通信速度は仮置き。解決時期: 段階3-2。TBD-017 GPIO割り当てが未定のため、観測対象のピンは未確定。解決時期: 段階3-2。

**前提条件**

- SWR_004 を実装したソフトウェアが RP2040 実機で動作していること
- I2C の SCL（Serial Clock Line、シリアルクロック線）と SDA（Serial Data Line、シリアルデータ線）をロジックアナライザまたはオシロスコープで観測できること

**手順**

1. I2C 初期化後、LCD1602 のアドレスに対してダミー書き込みを1回行う
2. SCL のクロック周波数を計測する
3. 9 クロック目における ACK（Acknowledge、受信確認応答）の有無を観測する

**合否基準**

- SCL の周波数が 100kHz ± 10% の範囲内であること
- スレーブから ACK が返ること（NACK ではないこと）
- バスがアイドル時に SCL・SDA ともに H レベルに保持されていること（プルアップが効いていること）
```

```{swverif} LCD1602の初期化シーケンスの確認
:id: SWV_006
:status: draft
:method: inspection
:environment: review
:verifies: SWR_005

**前提条件**

- SWR_005 を実装したソースコードが存在すること
- HD44780 のデータシートに記載された初期化シーケンスを参照できること

**手順**

1. LCD の初期化処理のソースコードを読み、送信するコマンド列とその順序を書き出す
2. HD44780 のデータシートが規定する 4 ビットモードの初期化シーケンスと突き合わせる
3. 各コマンド間のディレイの実装値を、データシートが要求する最小値と比較する

**合否基準**

- コマンド列と順序がデータシートの初期化シーケンスと一致すること
- 各ディレイがデータシートの要求する最小値以上であること
- PCF8574（I2C 経由の 8 ビット I/O エクスパンダ）への書き込みが上位 4 ビットと下位 4 ビットに分割されていること
```

```{swverif} LCD1602への表示成立の確認
:id: SWV_007
:status: draft
:method: demonstration
:environment: target
:verifies: SWR_005

**前提条件**

- SWR_004 と SWR_005 を実装したソフトウェアが RP2040 実機で動作していること
- LCD1602 が接続され、目視できること

**手順**

1. 初期化後、既知の文字列を 1 行目と 2 行目に書き込む
2. 表示内容を目視で確認する

**合否基準**

- 意図した文字列が意図した行・桁位置に表示されること
- 文字化け、欠落、ゴースト表示がないこと
```

SWR_005 の初期化シーケンスの妥当性は、表示ができることでは保証されない。
ディレイが不足していても室温では動作してしまい、個体差や温度条件で失敗する不具合になるため、
データシートと突き合わせを検査として分離する。一方で配線やアドレス指定の誤りは検査では見つからないため、実機での表示検証も行う。

```{swverif} 表示更新周期の計測
:id: SWV_008
:status: draft
:method: test
:environment: target
:verifies: SWR_006
:open_params: TBD-001 表示周期500msは仮置きのため、合否基準の値は連動して変わる。解決時期: 段階4-4。

**前提条件**

- SWR_006 を実装したソフトウェアが RP2040 実機で動作していること
- LCD への書き込み開始時点を GPIO のトグルまたは I2C バスの通信開始で観測できること

**手順**

1. LCD 表示更新の開始時点を観測できる状態にする
2. 60 秒間動作させ、更新間隔を全て記録する

**合否基準**

- 更新間隔の平均が 500ms ± 10ms の範囲内であること
- 記録した全区間において、更新間隔が 500ms を下回らないこと
```

SWR_006 は「500ms 周期で更新する」ことに加えて「500ms 未満の周期で更新しない」ことを要求している。
平均値だけでは後者を確認できないため、全区間の最小を合否基準に含める。
