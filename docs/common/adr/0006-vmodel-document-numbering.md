# ADR-0006: V字構造を反映した文書採番体系

## ステータス

採択（2026-09-04、issue #69 にて決定）

## 文脈

`docs/common/` の文書は ASPICE プロセス順の 10 刻みで採番している。設計側（00〜50）は
V 字の左を降りる順に並んでおり問題ないが、検証設計側（60〜80）は 60 統合 →
70 コンポーネント → 80 ユニットの順で、V 字の右を降りる向きに並んでいた。

この並びには 2 つの問題がある。

1. **番号の大小が V 字上の位置と一致しない。** 60 は V 字の最も右上（統合検証）で
   ありながら、より下位のユニット検証（80）より小さい番号を持つ。「番号が大きいほど
   工程が後ろ」という 10 刻み体系の前提が右半分で崩れる。
2. **SWE.1 と対になる検証設計の置き場所がない。** SWE.6 は実施段階（段階4-4）だけが
   存在し、設計文書も設計段階も定義されていなかった。V 字が 1 ペア欠けた状態で、
   80 の次に置くと今度は「番号が大きいほど下位」という右半分の規則にも反する。

あわせて、準拠する規格の版が明記されていなかった。`00_overview.md` と `CLAUDE.md` は
「ASPICE V字モデルに準拠する」とだけ書いており、SWE.6 を「受け入れテスト」と呼んで
いた。この呼称は 3.1 の Software Qualification Test（適格性確認テスト）とも、
4.0 の Software Verification とも一致しない。

60〜80 の文書はまだ 1 つも作成していないため、リナンバーによる参照破壊が起きない。
最初の検証設計文書を作成する直前が、体系を変更できる最後の機会である。

## 検討した選択肢

### 選択肢A: 現行の並びを維持し、SWE.6 を 90 に置く

利点：

- 変更が最小で済む。既存の記述を書き換える必要がない

欠点：

- 右半分の並びが「60 統合 → 70 コンポーネント → 80 ユニット → 90 ソフトウェア検証」と
  なり、番号と V 字上の位置の対応が説明不能になる。90 は 60 より上位の検証である
- 規則を言葉で説明できない体系は、将来の文書追加のたびに判断を要する

### 選択肢B: 設計と検証設計を隣接させる（20、25、30、35 …）

利点：

- ペアが視覚的に隣り合う。対応関係が最も読み取りやすい

欠点：

- 10 刻みは、SWE.1 の文書を分割する場合や補足資料を足す場合に備えて 21〜29 を
  空けてある設計である。25 を使うとその余地を半分潰す
- 番号体系の目的（後からの挿入に耐える）そのものを損なう

### 選択肢C: V 字を一周する昇順に振り直す

利点：

- 「番号が大きいほど V 字の後ろ、検証設計なら番号が大きいほど上位」という規則 1 本で
  全体を説明できる
- ペアの和が 110 で一定になり、対応関係が算術的に検証できる
- 10 刻みの余地を維持したまま SWE.6 を 90 に収められる

欠点：

- 60〜80 の記述を持つ 4 ファイルの書き換えが必要（ファイル実体は未作成のため
  リネームは発生しない）

## 決定

選択肢C を採用する。あわせて準拠する版を Automotive SPICE 4.0（PAM v4.0）と定める。

### 準拠する版

**Automotive SPICE 4.0** に準拠する。新規に構築するプロセスで旧版を採用する理由がなく、
現行の評価基準が 4.0 であるため。

版によって V 字右側のプロセス名称が異なる。

| プロセス | 3.1 | 4.0（本プロジェクト） |
|---|---|---|
| SWE.4 | Software Unit Verification | Software Unit Verification |
| SWE.5 | Software Integration and Integration Test | Software Component Verification and Integration Verification |
| SWE.6 | Software Qualification Test | Software Verification |

4.0 の SWE.6 は、統合されたソフトウェアがソフトウェア要件を満たすことを検証する
プロセスである。「適格性確認テスト」は 3.1 の名称であり 4.0 には存在しない。
「受け入れテスト」はいずれの版でも SWE.6 の名称ではない。

SWE.2.1 / SWE.2.2 および SWE.5.1 / SWE.5.2 の細分は規格上の区分ではなく、本プロジェクト
独自の記法である。4.0 の SWE.5 は「コンポーネント検証」と「統合検証」の 2 側面を
1 プロセスに含む。細分番号は本プロジェクトで先に定めた SWE.5.1 = 統合検証、
SWE.5.2 = コンポーネント検証を維持する。公式名称の語順（コンポーネント検証 →
統合検証）とは逆になるが、既存の記述との整合を優先する。

### 文書番号

| 番号 | 文書 | プロセス | 作成段階 |
|---|---|---|---|
| 00 | `00_overview.md` | — | — |
| 10 | `10_system_requirements.md` | SYS.2 | 段階1 |
| 20 | `20_software_requirements.md` | SWE.1 | 段階1 |
| 30 | `30_architecture.md` | SWE.2.1 | 段階2.5-1 |
| 40 | `40_component_design.md` | SWE.2.2 | 段階2.5-2 |
| 50 | `50_detailed_design.md` | SWE.3.1 | 段階2.5-3 |
| 60 | `60_unit_verification_design.md` | SWE.4 | 段階2.5-3 |
| 70 | `70_component_verification_design.md` | SWE.5.2 | 段階2.5-2 |
| 80 | `80_integration_verification_design.md` | SWE.5.1 | 段階2.5-1 |
| 90 | `90_software_verification_design.md` | SWE.6 | 段階2.5-0-4 |
| 99 | `99_traceability.md` | — | — |

設計文書とそれに対応する検証設計文書は、番号の和が 110 になる。

```text
20 ←→ 90   SWE.1  ←→ SWE.6     段階2.5-0
30 ←→ 80   SWE.2.1 ←→ SWE.5.1  段階2.5-1
40 ←→ 70   SWE.2.2 ←→ SWE.5.2  段階2.5-2
50 ←→ 60   SWE.3.1 ←→ SWE.4    段階2.5-3
```

あわせて、SWE.6 の設計を行う段階として段階2.5-0-4（ソフトウェア検証設計）を新設する。

## 理由

採番体系に求めるのは、新しい文書を追加するときに置き場所が一意に決まることである。
選択肢A は既存の文書には対応できるが、次に文書が増えたときの判断基準を与えない。

ペアの和が 110 で一定という性質は、単なる語呂合わせではなく検証手段になる。設計文書と
検証設計文書のペアを誤って記述した場合、和が 110 にならないことで機械的に検出できる。
将来 `metadata_lint.py` にルールとして追加する余地がある。

10 刻みの余白を守ることを選択肢B より優先した。本プロジェクトは要件 ID について永久欠番の
方針を採っており、一度決めた体系を後から変えないことを重視している。文書番号でも
同じ姿勢を採る。

## 影響

ポジティブな影響：

- 文書番号から V 字上の位置が一意に読み取れる
- SWE.6 の設計段階が定義され、V 字の欠けが埋まる
- 段階2.5 の各サブ段階が「設計 + 対になる検証設計」の形で統一される
- 準拠する版が明記され、プロセス名称の正しさを機械的に照合できるようになる

ネガティブな影響：

- 段階2.5-0 に新しいサブ段階が増え、段階2.5-1 の着手が後ろにずれる
- 本 ADR 以前に書かれた外部記事や issue が旧採番・旧呼称を参照している場合、齟齬が残る
- 4.0 の用語変更のうち Output Work Products → Information Items は未反映であり、
  版の準拠が部分的である

将来の見直し条件：

- PAM 4.1 が正式リリースされ、V 字右側のプロセス定義に変更があった場合
- Information Items への用語統一を行う場合、本 ADR に追記または新 ADR を起こす
