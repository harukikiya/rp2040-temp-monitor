# ADR-0005: 要件承認ゲートの定義

## ステータス

採択（2026-08-22、PR #60 にて採択）

段階2.5-0-3（PR #62 / #64 / #66 / #68）でシステム要件 7件・ソフトウェア要件 38件の承認判定に適用済み。
構造的 TBD（TBD-016）を持つ SWR_030 の1件は基準1により承認を見送り、段階2.5-1へ申し送りとした。

## 背景

要件は 56 件すべて `status: draft` である。段階2.5（設計フェーズ）に進むにあたり、
どの要件を根拠に設計してよいのかを決める必要がある。

しかし `docs/conf.py` の `needs_warnings` には `approved_with_tbd`
（`tbd_items` を持つ要件を `approved` にすると警告）が設定されており、`make html` は
`-W` 付きで実行される。したがって TBD を持つ 14 件は承認できない。

さらに TBD 15 項目の大半は「実機で確認後に決定」型である。LCD も ADC も未実装の現段階では
原理的に解決できない。つまり **「全要件を approved にしてから設計に進む」は成立しない。**

一方、全件 `draft` のまま設計に進むなら `status` は情報を持たない飾りになる。
`approved` が一度も使われない enum 値なら、定義してある意味がない。

ASPICE SWE.1 は合意された要件を求めるが、要件が未確定値を含んではならないとは言っていない。
承認とは「この要件で次工程に進んでよい」という合意であって、「もう一文字も変わらない」という
宣言ではない。問題は承認そのものではなく、**承認の判定基準が定義されていないこと** にある。

## 検討した選択肢

### 選択肢A: すべての TBD を解決してから承認する

利点：

- 承認の意味が最も強い。`approved` は完全確定を意味する

欠点：

- 実機依存の TBD は段階4 まで解決できない。設計フェーズに入れず、プロジェクトが停止する
- 「工程の順序を守るために順序が壊れる」という自己矛盾に陥る

### 選択肢B: `approved_with_tbd` 警告を削除し、TBD の有無を承認と無関係にする

利点：

- 実装が最も容易（`conf.py` の 1 行削除）

欠点：

- 通信機構が未定といった「設計できない要件」まで承認できてしまう
- ゲートが何も止めなくなり、`approved` の情報量がゼロになる
- 実機調整の宿題が本文中の散文として散らばったまま残り、一覧できない

### 選択肢C: TBD を区分し、設計を妨げるものだけが承認を阻む

利点：

- 承認が「設計を開始してよいか」という実務的に意味のある判定になる
- 止めるべきものだけが止まる
- パラメータは段階4 への宿題として明示的に残る

欠点：

- フィールドが 1 つ増える
- 区分の判定に人間の判断が要り、機械化できない

### 選択肢D: `status` に承認の段階を追加する（例: `approved_for_design`）

利点：

- 既存の `approved` の意味を変えずに済む

欠点：

- 承認者が 1 人の本プロジェクトでは、同じ人が同じ日に両方を付けることになり実態がない
- `needs_types` の enum、ダッシュボード、警告フィルタのすべてに波及する

## 決定

**選択肢C を採択する。**

### 1. 承認の単位

承認の単位を「要件の内容が確定したか」ではなく **「設計を開始してよいか」** とする。

### 2. TBD の 2 区分

TBD を 2 種類に分け、格納フィールドで区分を表す。

| 区分 | 意味 | 承認への影響 | フィールド |
|---|---|---|---|
| 構造的 TBD | 要件の構造・インタフェースが未定。設計できない | 阻む | `tbd_items`（既存） |
| パラメータ TBD | 値の調整のみ。構造は確定しており設計できる | 阻まない | `open_params`（新設） |

区分の判定基準は次の 1 点とする。

> **その項目を決めないと、要件を満たすモジュールのインタフェースまたは制御構造が書けないか。**

書けないなら構造的、値を差し替えるだけで済むならパラメータである。

### 3. `open_params` の書式

`open_params` には解決時期を必ず書く。書式は次のとおり。

```text
TBD-nnn 内容。解決時期: 段階N。
```

段階番号には「その値を実際に閉じられる最も早い段階」を書く。1 つの要件が複数の
パラメータを持つ場合は、項目ごとに解決時期を書く。

### 4. 承認基準

要件を `approved` にする条件は次の 5 項目とする。

| # | 条件 | 判定 |
|---|---|---|
| 1 | `tbd_items` が空である（構造的 TBD が無い） | 機械（`approved_with_tbd`） |
| 2 | 親要件へのトレースがある（`refines` が設定済み） | 機械（`swr_without_parent`） |
| 3 | 段階4 で合格・不合格を判定できる書き方である | レビュー |
| 4 | 実装手段ではなく、満たすべきことが書かれている | レビュー |
| 5 | `open_params` がある場合、解決時期が明記されている | 機械（`open_params_without_due`） |

### 5. 検査の実装

- `needs_fields` に `open_params` を追加する
- `needs_warnings` に `open_params_without_due` を追加する
- 既存の `approved_with_tbd` は変更しない。「構造的 TBD は承認を阻む」という意図が
  そのまま活きるため

### 6. TBD 番号の運用

TBD 番号は通番とし、リナンバーしない。解決済み・統合済みの番号は欠番として残す。
要件 ID と同じ運用である（過去の issue・PR・コミットからの参照を壊さないため）。

本 ADR 適用時点の欠番は次のとおり。

| 番号 | 理由 |
|---|---|
| TBD-005 | TBD-012（SWR_015）と同一のパラメータのため統合 |
| TBD-009 | 採番時の飛ばし。一度も使われていない |
| TBD-014 | ADR-0002 で解決済み（SIO FIFO を採択） |
| TBD-015 | ADR-0002 の決定に基づき SWR_028 が規定済み |

### 7. 再承認の運用

承認後に要件の内容を変更した場合は次のとおり扱う。

| 変更の種類 | 扱い |
| --- | --- |
| 意味が変わらない修正（誤字、表記統一、参照先の追記） | `approved` のまま。PR 本文に理由を書く。 |
| 検証条件が変わる修正（値、範囲、対象、判定基準） | `draft` に戻し、承認基準で再判定する。 |
| `open_params` の値を確定させる修正（段階4 の実機調整） | `approved` のまま。確定した項目を `open_params` から削除する。 |
| 構造的 TBD の追加 | `draft` に戻す（`approved_with_tbd` が機械的に抽出する）。 |

差し戻す場合は、その要件を親に持つ設計・テスト成果物への影響を PR 本文に記載する。
判断に迷う場合は `draft` に戻す。承認は取り直せるが、誤った承認は下流に伝播する。

### 8. 基準4 の適用範囲

要件の主語がレイヤ名・モジュール名であること（「ADCドライバは」「アプリケーション層は」等）は基準4 の違反とみなさない。

本プロジェクトはレイヤ構成を ARC_001 で前提として確定させており、全 SWR が `layer` フィールドを持つ。
その前提の上で「どの層が何を満たすか」を書くことは、要件の粒度を下げる行為ではなく、確定済みの構造への割り付けである。

ただし `layer` フィールドと本文の主語が食い違っている場合は、例外ではなく誤りとして修正する。

## 理由

### なぜ選択肢C か

判断の分かれ目は「ゲートが実際に何かを止めるか」である。

本 ADR 適用時点で承認を阻むのは **SWR_030 の 1 件のみ** である。これは「FIFO 満杯時に
待つか、古いデータを捨てるか、警告を返すか」という未決定事項であり、選択によって送信 API の
契約（戻り値の有無・ブロッキングの有無）が変わる。ADR-0002 自身が「FIFO 満杯時の挙動を
別途決める必要がある」と明記しており、実在する未決事項である。

1 件しか止まらないという事実は正直に記しておく。選択肢C の価値は現時点の件数ではなく、
次の 2 点にある。

1. **前向きの効果。** 段階2.5-1 以降で追加されるアーキテクチャ設計・コンポーネント設計・
   テスト設計は、作成時点で必ず未決定事項を含む。ゲートが無ければそれらは無検査で
   `approved` になる。
2. **宿題の可視化。** 選択肢B では実機調整の宿題が本文中の散文として散らばったまま残る。
   `open_params` と解決時期の必須化により、段階4 で閉じるべき項目が機械的に一覧できる。

### なぜ選択肢D でないか

承認者が 1 人の個人プロジェクトで承認の段階を増やしても、同じ人が同じ日に両方を付ける。
ステータスの粒度は意思決定の粒度に合わせるべきであり、それより細かくすると形骸化する。
複数人開発になった時点で再検討する。

### なぜ解決時期を必須にするか

実測に基づく。現在の `tbd_items` 15 項目のうち、解決時期が読み取れるのは
「実機動作確認後」「実機計測後」といった表現のみで、**どの段階で閉じるのかは 1 件も
書かれていない。** 期限のない宿題は忘れられる。段階番号まで書かせ、`-W` で強制しなければ
この曖昧さは残る。

## 検証

sphinx-needs のフィルタが日本語の部分文字列判定を評価できるかを実測した
（sphinx 9.1.0 / sphinx-needs 8.0.0 / myst-parser 5.0.0。`uv.lock` の解決版）。

- `open_params` を `needs_fields` に追加すると `needs.json` に出力される。
  linter とダッシュボードから参照できる
- `'解決時期:' not in open_params` を含むフィルタは正しく評価される。解決時期を書いた
  要件は通過し、書かなかった要件のみが検出される
- `-W` 付きビルドは、違反ありで終了コード 1、違反なしで 0 を返す
- `needtable` の `:columns:` に `open_params` を指定して描画できる

## 影響

ポジティブな影響：

- 機械チェックを通過する要件が 55 件になり、段階2.5 に進める（承認保留は SWR_030 の 1 件）
- 段階4 の実機調整タスクが `open_params` として機械的に一覧できる
- ADR-0002 で既に解決済みだった TBD-014・TBD-015 が要件側に残っていた不整合が解消される

ネガティブな影響（技術的負債を含む）：

- 区分の判定は人間の判断であり、機械検査できない。構造的なものをパラメータに誤分類すると
  ゲートは素通りする。レビューで担保するしかない
- `open_params` は自由文字列であり、書式検査は「解決時期:」の有無しか見ない。
  書かれた段階番号が実在する段階かは検査されない
- 承認基準 3・4 はレビュー判定であり、承認の再現性は完全ではない

関連する要件：

- 承認保留となるのは SWR_030
- ADR-0002 参照へ切り替えるのは SWR_022、SWR_023
- `open_params` を持つのは SYS_001、SYS_002、SYS_003、SYS_004、SWR_004、SWR_012、
  SWR_015、SWR_017、SWR_033、SWR_038

将来の見直し条件：

- 複数人開発になり、起票者と承認者が分かれたとき（選択肢D を再検討する）
- 構造的 TBD が恒常的に空になったとき（`approved_with_tbd` の存続を再評価する）
