# ADR-0004: メタデータの階層管理と機械検証

## ステータス

採択（2026-08-12、PR #37 にて採択）

`scripts/metadata_lint.py` として CI で稼働中。MD01〜MD08・SRC01・XR01 の各ルールを毎 PR で検証している。

## 背景

ドキュメントとコードの読者に、人間に加えて AI（レビュワー・RAG・エージェント）が第一級で
加わった。AI にとって「この文書は何か・どの要件の話か・いつ時点か」は、構造化された
メタデータとして与えられなければ検索精度・引用の正確さが落ちる（メタデータ付き検索
82.5% vs 本文のみ 73.3% precision という報告がある）。

一方、本プロジェクトは sphinx-needs により**オブジェクト単位の強いメタデータ**
（`:id:` `:status:` `:layer:` `:refines:` 等の型付き属性）を既に持つ。ここに文書単位・
コード単位のメタデータを無計画に足すと二重管理が生じ、検証されないメタデータは腐って
「AI に誤った確信を与える」という、無いより悪い状態になる。

設計書（30/40/50 番台の本格版）は未着手であり、執筆規約を含めて方向を決めるなら今が
最後の低コストな機会である。詳細な調査と分析は別紙
`learning/metadata.md`（メタデータ方針 — 調査記録）に置く。

## 決定

1. **メタデータを階層で管理し、各層の役割を排他にする。**
   - L1 リポジトリ層: `CLAUDE.md` / `README`（エージェントの入口）
   - L2 ドキュメント層: YAML frontmatter（文書の種類・対応プロセス・文書間関連）
   - L3 オブジェクト層: sphinx-needs 属性（要件・設計・テストの ID / 状態 / 型付きリンク）
   - L4 コード層: Doxygen タグ + `@satisfies <ID>` トレースタグ
   - 導出層: `needs.json` / Doxygen XML（集約はビルドが生成し、手書きしない）

2. **frontmatter は OKF 互換コア + 最小拡張とする**（スキーマ v0）:
   必須 `type`（requirements / design_doc / adr / learning / test_design / progress）、
   任意 `title` / `description` / `tags` / `doc_id` / `aspice` / `stage` / `relates`。
   **意図的に書かないもの**: `timestamp`・版数（git が知っている）、`status`（needs と
   二重管理）、`author`（git blame が知っている）。
   MyST `-W` との相性は実ビルドで検証済み（sphinx 9.1.0 / myst-parser 5.0.0 /
   sphinx-needs 8.0.0。未知拡張キーを含むスキーマが警告ゼロで通過し、frontmatter は
   HTML に描画されない）。既存文書への付与は本 ADR のスコープ外（別途の比較実験の
   結果を反映して実施）。

3. **コード→要件トレースは `@satisfies SWR_xxx` の1形式に統一**し、Doxygen ALIASES で
   描画しつつ、主消費者は機械抽出（/check-trace と linter）とする。適用は段階3の最初の
   SWR 実装から。既存起動コードは #21 の SWR 化後に遡及付与。ALIASES の描画形式
   （`\par` か `\xrefitem` 逆引きページか）は適用時に検証する。

4. **`needs_build_json = True` を conf.py に設定し、needs.json を常時出力する。**
   これが linter・レビュワー・将来の RAG の突合先（メタデータの導出層）になる。

5. **メタデータは CI で機械検証する**（原則 P4「検証されないメタデータは腐る」）。
   `scripts/metadata_lint.py` を導入し、必須フィールド・列挙値・禁止フィールド・
   `relates`/`@satisfies` の参照実在性（needs.json / ADR ファイル突合）を PR ごとに検査。
   未知キーは warning（OKF の未知キー許容原則）、禁止フィールドと参照切れは error。
   frontmatter 未付与の既存文書があるため、当面 `frontmatter_required: false` で運用し、
   付与完了後に true へ切り替える。

6. **執筆規約を RAG/チャンク前提に合わせる**: 1見出し1トピック、ID の明示
   （「この要件」ではなく「SWR_002」）、1ファイル1概念、チャンク単独で自己完結する記述、
   図は PlantUML ソース併置。

7. **原則**（フィールド追加・変更時の判定基準）:
   P1 導出可能なものは手書きしない ／ P2 消費者のいないメタデータは書かない
   ／ P3 ID を貫通させる ／ P4 CI で検証する ／ P5 人間の可読性を犠牲にしない。

## 検討した代替案

- **frontmatter に status/日付も持たせる（フル frontmatter）**: 文書単体では便利だが、
  needs の status と必ず乖離する。二重管理の腐敗リスクが利便を上回るため不採用。
- **OKF の完全準拠（index.md / log.md 予約ファイル含む）**: v0.1 公開1ヶ月であり、
  予約ファイル規約まで追うのは早い。frontmatter という下位互換部分のみ採用し、
  完全準拠は OKF エコシステムの成立を見て再判断。
- **メタデータを導入しない（本文+needs のみ）**: L3 だけでは文書単位の絞り込み
  （RAG の filtering、エージェントの文書選別）ができない。文書層の薄い1枚は必要。
- **mlx.traceability 等への乗り換え**: sphinx-needs で既にトレーサビリティが成立して
  おり、乗り換えの利得がない。

## 帰結

- 設計書はこの規約で書き始められる（後からの一括改修が不要になる）。
- CI に metadata lint ジョブが増える（needs.json 生成を含む docs ビルドの後段で実行）。
- スキーマ v0 の変更は本 ADR の改訂または新 ADR を要する。フィールド追加は
  P2（消費者の明記）を必須条件とする。
- ADR は連番・欠番なしの規約により本決定が 0004 を取る。計画中の「Rust 移植を
  見越した設計を敢えてしない」判断の ADR は 0005 以降となる。
- 将来 RAG を導入する場合も、本決定の執筆規約・ID 規律・needs.json がそのまま
  インデックスの入力になる。
