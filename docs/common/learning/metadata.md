## 0. 目的と適用範囲

**なぜ今か。** ドキュメントとコードの読者に、人間に加えて AI（レビュワー・RAG・エージェント） が第一級で加わった。人間は文脈を行間から補えるが、AI は「この文書は何か・どの要件の話か・いつ時点の話か」を構造化された形で与えられないと、検索の精度も引用の正確さも落ちる。メタデータはその構造化情報の置き場所である。

**適用範囲。** ①設計書群（`docs/`、Sphinx + MyST + sphinx-needs）、②ソースコードのコメント（`firmware-*/`、Doxygen）、③将来の RAG / エージェント基盤への入力。

## 1. 一般論の調査結果（2026-07 時点）

### 1.1 OKF（Open Knowledge Format）

Google Cloud が 2026-06-12 に公開した v0.1 仕様。「Markdown ファイルのディレクトリ + YAML frontmatter」という LLM-wiki パターンを相互運用可能な形に標準化したもの。要点：

- **必須フィールドは `type` の1つだけ**。推奨オプションは `title` / `description` / `resource` / `tags` / `timestamp`。それ以外は producer の自由（consumer は未知キーを許容する義務）。
- **ファイルパス = 概念の ID**（`tables/user.md` → `tables/users`）。**通常の Markdown リンクが概念間のグラフ**になる。
- 予約ファイル名：`index.md`（段階的開示 - エージェントが階層を辿るための目次）、`log.md`（変更履歴）。
- 設計思想：「仕様が定めるのは相互運用の表面であって、コンテンツモデルではない」「producer と consumer の独立（フォーマットが契約）」。
- RAG との関係：OKF 自身は「キュレーション済み・バージョン管理された知識をエージェントが直接読む」形を志向し、RAG と**排他ではなく補完**の位置づけ。

**本プロジェクトへの示唆**：別途の比較実験で「OKF 風 frontmatter」を試す判断は、公開1ヶ月の仕様に賭けるというより、**OKF が標準化した下位互換パターン（frontmatter 付き Markdown）に乗る**ということ。仕様が変わっても frontmatter という形式自体は Obsidian / Hugo / MyST が10年来使う枯れた形式であり、リスクは低い。

### 1.2 RAG におけるメタデータの4つの役割

調査から、メタデータが RAG で果たす役割は次の4つに整理できる。**フィールドを設計するときは「どの役割の消費者がいるか」を必ず問う**こと。

| 役割 | 内容 | 根拠・数字 |
| --- | --- | --- |
| ①絞り込み（filtering） | ベクトル検索の**前に**属性で候補を削減する（例：`layer == driver` かつ `status == approved` のみ検索）。ガバナンス（機密区分・鮮度閾値）もここ | IEEE 系研究の報告でメタデータ付き検索 82.5% vs 本文のみ 73.3%（precision）。ガバナンス済みメタデータでエージェントの SQL 精度 +38% という報告も（Atlan）。
| ②引用・追跡（citation） | 回答がどの文書のどの節から来たのかを指せるようにする。**安定したチャンク ID**（ソース ID + 節）が評価・再現の前提 | 実務ガイド共通。「チャンク ID が ingestion 更新を跨いで安定しないと信頼できる評価がない」 |
| ③鮮度（freshness） | `timestamp` による古い情報の除外・優先度付け | OKF の推奨フィールドでもある |
| ④埋め込み強化（enrichment） | メタデータを本文と**一緒に**埋め込む。2025年末の研究（arXiv:2512.05411）では、メタデータを本文の前置きとして結合して埋め込む prefix-fusion が、別ベクトルの線型結合より一貫して優位 | 同研究では「メタデータの統合方法はチャンキング戦略の選択と同程度に効く」と結論 |

### 1.3 チャンキングとメタデータは共同設計

- チャンク境界は**自然な境界（見出し）**に揃えるのが基本。事実検索なら 256-512 トークン、文脈重視なら 512-1,024。オーバーラップは 10-20% から。
- **文書側の frontmatter は、チャンク分割時に各チャンクの metadata へ伝播させる**のが定石。つまり「文書をどう書くか」が「チャンクがどんなメタデータを持てるか」を規定する - 執筆規約とインデックス設計は不可分。
- 検索は「メタデータフィルタ + ベクトル検索」のハイブリッドが本番品質の分水嶺、という報告が複数。

### 1.4 トレーサビリティ系（docs-as-code）の実践

- **sphinx-needs は docs-as-code の要件管理のデファクト**。need オブジェクトが `id` / `status` / `tags` リンク属性を持ち、ISO 26262 / DO-178 / ASPICE 対応の設定が可能。`needs.json` としてエクスポートできる。
- 類種に mlx.traceability（Melexis、ASPICE/ISO26262 向け。命名規則ガイドライン込みで運用）など。共通パターンは「**一意 ID + 型付き関係（addresses / tested_by 等） + 双方向マトリクス自動生成**」。
- ここから言えるのは、**要件 ID を軸にした型付きリンクこそが docs-as-code 界の「メタデータ管理」の中核**だということ。frontmatter はその外側（文書単位）を補う存在。

## 2. 本プロジェクトへの含意（Fable の分析）

### 2.1 最重要の認識：このプロジェクトは既にメタデータシステムを持っている

sphinx-needs の要件ブロックは、それ自体が構造化メタデータである：

```
:id: SWR_002 / :status: draft / :type_kind: Functional / :layer: driver
:refines: SYS_001 / :rationale: ... / :tbd_items: ...
```

これは OKF の frontmatter より**粒度が細かく型が強い**（文書単位ではなく、オブジェクト単位、リンクが型付き）。したがって方針の出発点は「メタデータを新規導入する」ではなく、**「オブジェクト層の強いメタデータ（needs）に、文書層（frontmatter）とコード層（Doxygen）を整合的に足す」**である。frontmatter に needs と同じ情報を書くのは二重管理であり、腐る。

### 2.2 メタデータの階層モデル

| 層 | 担体 | 粒度 | 主な消費者 | 現状 |
| --- | --- | --- | --- | --- |
| L1 リポジトリ層 | `CLAUDE.md` / `README.md` / `index.md` | リポジトリ | エージェントの入口（OKF の `index.md` = 段階的開示に相当） | あり |
| L2 ドキュメント層 | YAML frontmatter | ファイル | RAG の①絞り込み・③鮮度、エージェントの文書選別 | **未導入(DOC-7)** |
| L3 オブジェクト層 | sphinx-needs 属性 | 要件・設定・テスト単位 | トレーサビリティ、/check-trace、RAG の②引用 | あり（強い） |
| L4 コード層 | Doxygen タグ + トレースタグ | ファイル・関数 | API ドキュメント、コード↔︎要件トレース | Doxygen あり/**トレースタグ未導入** |
| 導出層 | `needs.json` / Doxygen XML | 集約 | 構造化クエリ（= API）、レビュワー、将来の MCP | ビルドで生成 |

### 2.3 ID が外部キーである

`SWR_002` のような ID は、docs・コード・テスト・issue を貫く **json key**。RAG の回答が「SWR_002 によれば...」と言えて、それを人間が `needs.json` で検証できる - この**引用の検証可能性**が、AI 出力を「読んで信じる」から「ゲートで受ける」に変える鍵。ID の規律（一意・不変・機械抽出可能な表記）はメタデータ方針の中で最も費用対効果が高い。

## 3. 方針（規範）

### 3.1 原則

- **P1：Single Source of Truth。**導出可能なものは手書きしない。日付は git が知っている。集約は `needs.json` が担う。手書きするのは「機械が導出できない意味」だけ。
- **P2：消費者のいないメタデータは書かない。**フィールドを足すときは、それを読む処理（レビュワー・RAG　フィルタ・CI）を同時に言えること。
- **P3：ID を貫通させる。**要件 ID・ADR 番号・issue 番号は、本文・コメント内で `SWR_002` / `ADR-0003` / `#34` の正規表現で書き、機械抽出（grep）可能に保つ。
- **P4：検証されないメタデータは腐る。**スキーマ必須項目・許容値・ID 実在性は CI で lint する（腐ったメタデータはないより有害 - AI に誤った確信を与える）。
- **P5：人間の読み物としての品質を落とさない。**　frontmatter は最小限。本文の可読性を犠牲にしてまで構造化しない（構造は needs とリンクが担う）。

### 3.2 ドキュメント層：標準 frontmatter スキーマ（案）

OKF 互換のコア + プロジェクト拡張。**MyST `-W` との相性は実ビルドで検証済み**（2026-07-13、sphinx 9.1.0 / myst-parser 5.0.0 / sphinx-needs 8.0.0。未拡張キーは含む本スキーマが警告ゼロで通過し、frontmatter は HTML へ一切描画されないことを確認）。既存文書への付与は別途行う。

``` yaml
---
# --- OKF 互換コア ---
type: design_doc        # 必須。requirements / design_doc / adr / learning /test_design / progress
title: ソフトウェア要件
description: SYS 要件をソフトウェアの振る舞いに分解した文書（ASPICE SWE.1）
tags: [aspice, swe1]
# timestamp は書かない（P1：git log から導出。書くなら CI が更新する）

# --- プロジェクト拡張 ---
doc_id: DOC-20          # 文書番号体系（20_software_requirements → DOC-20）
aspice: SWE.1           # 対応 ASPICE プロセス（①絞り込みの主要軸）
stage: "2.5"            # 主に関係する開発段階
relates: [ADR-0001]     # 文書レベルの関連（オブジェクトレベルのトレースは needs に任せる）
---
```

**書かないもの（意図的な不在）**：`status`（needs 側と二重管理になる。文書全体のステータスが必要になったら、その時に別名で導入を再検討）、`author`（git blame が知っている）、手動の日付・版数（P1）。

### 3.3 オブジェクト層：sphinx-needs は現行を維持

既存属性（`id` / `status` / `type_kind` / `layer` / `refines` / `rationale` / `tbd_items`）で十分。テスト設計段階（2.5）で `verified_by` 等のリンク型を追加する際は、**双方向で辿れる型付きリンク**として needs の設定に足す（frontmatter に書かない）。

### 3.4 コード層：Doxygen + トレースタグ

既存の Doxygen 規約（`@file` / `@brief` / `@details` / `@note` / `@name` グループ）は継続。追加するのは**コード→要件のトレースタグ**1種類：

``` c
/**
 * @brief ADC を初期化し温度センサチャネルを選択する。
 * @satisfies SWR_001
 */
```
- Doxyfile に `ALIASES += "satisfies=\par Satisfies:^^"` を定義して Doxygen 出力にも節として出す（**実装時に Doxyfile で描画を検証すること** - `\xrefitem` を使えば「要件別の逆引き一覧ページ」も生成できるが、まず単純形から）。
- **主要な消費者は grep**：将来の `/check-trace` コマンドが `@satisfies SWR_\d+` を抽出し、`needs.json` の ID 集合と突合して「実在しない要件を参照していないか」「実装リンクのない要件はどれか」を検査する。Doxygen の描画はおまけ、機械抽出が本体。
- 付与単位：要件を満たす**関数またはファイル**に付ける。行レベルには付けない（保守不能）。1関数に複数可。
- 適用開始：**段階3（実装フェーズ）の最初の SWR 実装から**。既存の起動コード（boot2/crt0）は #21 で SWR 化された後に遡及付与する。

### 3.5 RAG を見据えた執筆規約（いま守り始める）

RAG 導入前でも、次を守っておくと後のチャンギングがそのまま効く：

1. **1見出し = 1トピック**（見出しがチャンク境界になる。§1.3）
2. **見出し・本文に ID を明示**（「この要件は」ではなく「SWR_002 は」- チャンク単独で参照が解決できる = ②引用可能性）
3. **1ファイル 1概念に寄せる**（OKF の思想。`learning/linker.md` 62KB の分割 = DOC-6 はこの方針の実践第1号）
4. **代名詞・前方参照を減らし、チャンク単独で自己完結**させる（「前述のとおり」より「§2.1 の LMA/VMA 分離のとおり」）
5. **図は PlantUML ソースを併置**（画像だけの図は AI に不可視。テキストソースが検索・埋め込みの対象になる）

### 3.6 将来の RAG 導入時のインデックス設計指針

- チャンク：見出し境界、256-512 トークン起点、オーバーラップ 10-20% から調整。
- 各チャンクの metadata: L2 frontmatter（type / aspice / stage / tags） + 所属の need の属性（あれば id / status / layer）を伝播。埋め込みは **prefix-fusion**（メタデータ数行を本文先頭に結合して埋め込む）を第一候補に。
- チャンク ID：`パス#見出しスラッグ` で安定化（②引用・評価の前提）。
- 検索：**ハイブリッド**を既定とする - `needs.json` への構造化クエリ（完全一致・関係辿り）と、本文のベクトル検索の併用。「要件はドキュメントではなくデータベース」という発想は構造化側の思想。
- 注意：OKF 的な「エージェントがファイルを直接読む」経路と RAG は併存できる。小規模なうちは**直接読み + needs.json クエリで足りる**可能性が高く、RAG は文書量がエージェントのコンテキスト運用に収まらなくなってからで遅くない。

### 3.7 ガバナンス

- **スキーマのバージョン管理**：frontmatter スキーマは本書（将来は ADR）で版管理。フィールドの追加は「消費者の明記」（P2）を必須条件に。
- **CI lint**（INFRA 系 issue として起票）：①frontmatter の必須フィールド・許容値検査、②`@satisfies` 参照 ID の実在検査（`needs.json` 突合）、③（既存の）`sphinx-build -W`。
- **更新責務**：人が書くのは意味（description / tags / relates）、機械が書くのは事実（timestamp / 集約 / マトリクス）。

## 4. アンチパターン（やらないこと）

- **本文の複製をメタデータに書く**（description は1行要約。本文の要約更新漏れで乖離する）。
- **手動の日付・版数**（P1 違反。必ず腐る）。
- **消費者なきタグの乱発**（tags は①絞り込みで使う語彙に限定。自由連想タグは検索ノイズ）。
- **ステータスの二重管理**（needs の `status` と frontmatter に同種の情報を持たせない）。
- **画像だけの図**（AI に不可視。Excel 貼り付け UML の轍を frontmatter 時代に繰り返さない）。
